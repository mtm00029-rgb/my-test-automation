## レッスン 10-1: Visual Regression Testing

### このレッスンで学ぶこと
画面のスクリーンショットを前回と比較して、見た目の崩れを自動検出する。

### たとえ話
「間違い探しゲーム」の自動化。2枚の画像を重ねて、違いがあればハイライトしてくれるロボット。人間の目では見逃す1ピクセルのズレも検出できる。

### Playwrightのスナップショットテスト

```typescript
test('ログインページの見た目が変わっていない', async ({ page }) => {
  await page.goto('https://www.saucedemo.com/');
  await expect(page).toHaveScreenshot('login-page.png');
});
```

### 初回実行と比較
1. **初回**: 「正解の画像」が自動で保存される（ベースライン）
2. **2回目以降**: 現在の画面とベースラインを比較し、違いがあればテスト失敗
3. **意図的な変更**: `npx playwright test --update-snapshots` でベースラインを更新

### QA視点
CSSの変更が意図しないページに影響していないか、フォントや画像の表示崩れがないかを自動で検出できる。手動の目視確認を大幅に削減できる。

### 課題 10-1
1. Sauce Demoのログインページでスナップショットテストを書く
2. 初回実行でベースラインを作成する
3. ブラウザの幅を変えて実行し、レスポンシブデザインの崩れがないか確認する

## レッスン 10-2: アクセシビリティテスト

### このレッスンで学ぶこと
Webサイトが障がいのある方にも使いやすいかを自動でチェックする。

### たとえ話
建物の「バリアフリー検査」のWeb版。スロープがあるか、点字ブロックがあるかを検査するように、Webサイトの「使いやすさ」を検査する。

### axe-coreの導入

```bash
npm install -D @axe-core/playwright
```

### テストの書き方

```typescript
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('ログインページにアクセシビリティ違反がない', async ({ page }) => {
  await page.goto('https://www.saucedemo.com/');

  const results = await new AxeBuilder({ page }).analyze();

  expect(results.violations).toEqual([]);
});
```

### 検出できる問題の例
- 画像にalt属性（説明文）がない
- ボタンのコントラスト（文字と背景の色の差）が不十分
- フォームの入力欄にラベルが付いていない

### QA視点
アクセシビリティ対応は法的要件になりつつある（例：欧州アクセシビリティ法）。自動チェックを回せるQAエンジニアは市場価値が高い。

### 課題 10-2
1. `@axe-core/playwright` をインストールする
2. Sauce Demoの3ページ（ログイン、商品一覧、カート）にアクセシビリティテストを書く
3. 検出された違反を学習ログにまとめ、「深刻度（critical/serious/moderate）」で分類する

## レッスン 10-3: Docker基礎

### このレッスンで学ぶこと
テスト環境をDockerコンテナで統一し、「自分のPCでは動くのに...」問題を防ぐ。

### たとえ話
お弁当箱（コンテナ）に材料と調理器具を全部詰め込んで持ち運ぶイメージ。どこで開けても同じ料理が作れる。PCの環境が違っても同じテストが動く。

### Dockerのインストール
Docker Desktop を公式サイト（https://www.docker.com/products/docker-desktop/）からインストール。

### PlaywrightのDockerイメージ

```bash
# PlaywrightのDockerイメージでテストを実行
docker run --rm -v $(pwd):/work -w /work mcr.microsoft.com/playwright:latest npx playwright test
```

### コマンドの意味
- `docker run` — コンテナ（お弁当箱）を開く
- `--rm` — 実行後にコンテナを片付ける
- `-v $(pwd):/work` — 今のフォルダの中身をコンテナに渡す
- `mcr.microsoft.com/playwright:latest` — Playwright入りのお弁当箱を使う
- `npx playwright test` — テストを実行

### QA視点
チームメンバーのPCにNode.jsのバージョン違いがあっても、Dockerなら全員同じ環境でテストが動く。CI/CDでも同じイメージを使えば「ローカルでは通るのにCIで落ちる」問題を防げる。

### 課題 10-3
1. Docker Desktopをインストールする
2. PlaywrightのDockerイメージを使ってテストを実行してみる
3. ローカル実行との結果を比較して、差がないことを確認する

## レッスン 10-4: テスト戦略とテストピラミッド

### このレッスンで学ぶこと
「どのテストをどれくらい書くべきか」の全体戦略を理解する。

### テストピラミッド

```
        /  E2E  \          ← 少なめ（遅い・壊れやすい・でも信頼度高い）
       /----------\
      / Integration \      ← 中くらい（APIテストはここ）
     /----------------\
    /     Unit Tests    \  ← たくさん（速い・安定・開発者が書く）
```

### 各レベルの役割

| レベル | 誰が書く | 何をテストする | 速さ |
|--------|---------|---------------|------|
| Unit（単体） | 開発者 | 関数やメソッド単位 | 超速い |
| Integration（統合） | 開発者 + QA | API、サービス間の連携 | 速い |
| E2E（画面操作） | QA | ユーザーと同じ操作の流れ | 遅い |

### QAエンジニアの立ち位置
- **E2Eテスト**: QAの主戦場。ユーザー視点でのテストシナリオ設計はQAの専門領域
- **Integrationテスト（API）**: 開発者と協力して書く。QAが書けると非常に重宝される
- **Unitテスト**: 基本は開発者の領域。QAは「何をテストすべきか」の提案ができると良い

### なぜピラミッド型がよいか
E2Eテストだけを大量に書くと、実行に時間がかかり、メンテナンスも大変。下のレベルでカバーできるものは下で書き、E2Eは「重要なユーザーシナリオ」に絞るのがベストプラクティス。

### 課題 10-4
自分のプロジェクトのテストを「ピラミッド」に当てはめて分類する。E2Eに偏っていないか、APIテストで代替できるものはないかを分析し、学習ログにまとめる。

## よくあるエラーと対処法

### スナップショットテストが毎回失敗する
**原因**: フォントのレンダリングがOS/ブラウザで微妙に違う
**対処**: `maxDiffPixelRatio: 0.01` のように許容範囲を設定する。Dockerで環境を統一すると根本解決できる

### axe-coreで大量の違反が検出された
**原因**: テスト対象のアプリ自体にアクセシビリティの問題がある（デモアプリには多い）
**対処**: まずは `critical` と `serious` の違反に絞って対応。`minor` は後回しでOK

### Dockerコマンドが「permission denied」で動かない
**原因**: Docker Desktopが起動していない、またはユーザー権限の問題
**対処**: まずDocker Desktopを起動しているか確認。ターミナルで `docker --version` が表示されればインストールはOK
