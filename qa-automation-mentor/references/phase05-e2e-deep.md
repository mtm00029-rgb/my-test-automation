## 学習目標

CodeGen（操作の録画）に頼らず、自分の手でPlaywrightのテストコードを書けるようになる。

**たとえるなら**: カーナビ（CodeGen）なしでも、地図（ドキュメント）を読んで目的地にたどり着けるドライバーになること。

**QA視点**: CodeGenが生成するコードは動くが、壊れやすい。実務では「仕様変更に強いテスト」を書く力が求められる。

## レッスン 5-1: ロケーター戦略

### このレッスンで学ぶこと
画面上の要素（ボタンやテキスト）を「見つける方法（ロケーター）」を理解する。

### たとえ話
ロケーターは「住所」のようなもの。「東京都渋谷区の3番目のビル」（位置で指定）より「渋谷郵便局」（名前で指定）の方が、ビルが増えても見つけやすい。

### 優先順位（上ほど推奨）

```typescript
// 1. ロール（役割）で探す — 最も壊れにくい
page.getByRole('button', { name: '追加' })

// 2. テキストで探す — 表示文言がわかれば使える
page.getByText('TODOを追加')

// 3. ラベルで探す — フォーム入力で便利
page.getByLabel('タスク名')

// 4. テストIDで探す — 開発チームと相談して付けてもらう
page.getByTestId('add-button')
```

### なぜロールが一番良いのか
ロール（role）はHTMLの「意味」に基づくので、デザインが変わっても壊れにくい。これは、ユーザーが実際に画面をどう認識するか（「ボタンだ」「リンクだ」）と同じ視点でテストを書けるということ。

### 課題 5-1
TodoMVCアプリで、以下の3つの要素をCodeGenを使わずに手書きで見つけるテストを書く：
1. 新しいTODOを入力するテキストボックス
2. TODOの完了チェックボックス
3. 「Completed」フィルターリンク

## レッスン 5-2: ユーザー操作の幅を広げる

### このレッスンで学ぶこと
クリックと入力以外の操作（キーボード、チェックボックス、複数要素の検証など）をテストで再現する。

### 基本操作チートシート

```typescript
// テキスト入力 + Enterキー
await page.getByPlaceholder('What needs to be done?').fill('牛乳を買う');
await page.getByPlaceholder('What needs to be done?').press('Enter');

// チェックボックスの操作
await page.getByRole('checkbox').first().check();

// 要素の数を確認する
await expect(page.getByTestId('todo-item')).toHaveCount(3);

// テキストの内容を確認する
await expect(page.getByText('牛乳を買う')).toBeVisible();
```

### QA視点
マニュアルテストで「目で確認」していたことを、すべてコードの `expect` で書く。人間の目の代わりをロボットにやらせるイメージ。

### 課題 5-2
TodoMVCアプリで以下のシナリオを**1つのテストファイル**にまとめる：
1. TODOを3つ追加する
2. 2つ目のTODOを完了にする
3. 「Active」フィルターで未完了が2つ表示されることを確認する
4. 「Completed」フィルターで完了が1つ表示されることを確認する

## レッスン 5-3: 待機とテストの安定性

### このレッスンで学ぶこと
テストが「たまに成功してたまに失敗する」（フレーキー）問題の原因と対策を理解する。

### たとえ話
レストランで料理を注文して、1秒後に「料理がない！」と怒る人はいない。料理ができるまで「待つ」のが当然。テストも同じで、画面の表示を待ってから確認する必要がある。

### Playwrightの自動待機
Playwrightは賢くできていて、多くの場合は自動で「表示されるまで待つ」。ただし、以下のケースは注意が必要：

```typescript
// OK: Playwrightが自動で待ってくれる
await expect(page.getByText('保存しました')).toBeVisible();

// 注意: アニメーションや非同期処理がある場合
await expect(page.getByText('データを読み込み中...')).toBeHidden();
await expect(page.getByText('読み込み完了')).toBeVisible();
```

### やってはいけないこと

```typescript
// NG: 固定時間で待つ（遅いし不安定）
await page.waitForTimeout(5000);
```

**なぜNGか**: 5秒待っても足りない場合もあれば、1秒で十分な場合もある。「条件を満たすまで待つ」方が速くて安定。

### 課題 5-3
TodoMVCでTODOを追加→削除するテストを書き、`toBeVisible()` と `toBeHidden()` を両方使って「表示された → 消えた」を確認する。

## レッスン 5-4: デバッグとスクリーンショット

### このレッスンで学ぶこと
テストが失敗した時に「何が起きたか」を調べる方法を身につける。

### デバッグ方法（簡単な順）

**1. UIモード（最も直感的）**
```bash
npx playwright test --ui
```
タイムラインで失敗した瞬間の画面を確認できる。

**2. スクリーンショットの撮影**
```typescript
// テストの途中で画面を撮影
await page.screenshot({ path: 'debug-screenshot.png' });
```

**3. 失敗時のみ自動でスクリーンショット（設定）**
playwright.config.ts で以下を設定：
```typescript
use: {
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
}
```

### QA視点
マニュアルテストで「エビデンス（証拠）のスクリーンショット」を撮るのと同じ。自動テストでは失敗時に自動で証拠を残す仕組みを作っておくことが重要。

### 課題 5-4
playwright.config.ts に「失敗時のみスクリーンショットと動画を保存する」設定を追加し、わざと失敗するテストを書いて、証拠が保存されることを確認する。

## よくあるエラーと対処法

### 「locator.click: Target closed」
**原因**: ページが移動した後に、前のページの要素をクリックしようとした
**対処**: ページ遷移後に `await page.waitForURL(...)` で新しいページを待つ

### 「expect(locator).toBeVisible(): Timeout」
**原因**: 指定した要素が画面に見つからない（ロケーターが間違っている or 表示に時間がかかっている）
**対処**: まずUIモードで画面を確認し、正しいロケーターを調べる。Playwrightの「Pick locator」機能が便利。

### 「strict mode violation: locator resolved to X elements」
**原因**: ロケーターが複数の要素にマッチしてしまった（住所が曖昧で複数の家に届いてしまった状態）
**対処**: `.first()` で最初の要素を選ぶか、より具体的なロケーターに書き換える
