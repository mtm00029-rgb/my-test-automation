## 学習目標

これまで学んだ全スキルを組み合わせて、ポートフォリオとして見せられるテスト自動化プロジェクトを完成させる。

**たとえるなら**: 料理教室の卒業制作。個別に習った「焼く」「煮る」「盛り付け」の技術を全部使って、フルコースを完成させる。

**QA視点**: 実務では「テストが書ける」だけでなく「なぜそのテストを書いたか」を説明できることが重要。テスト計画書は、あなたのQA思考力を証明する武器になる。

## レッスン 9-1: テスト対象アプリの選定

### このレッスンで学ぶこと
ポートフォリオ用のテスト対象アプリを選ぶ。

### 推奨する練習用アプリ

| アプリ | 特徴 | URL |
|--------|------|-----|
| Sauce Demo | ECサイト風。ログイン・商品一覧・カート・購入 | https://www.saucedemo.com/ |
| TodoMVC | シンプルなTODOアプリ（すでに練習済み） | https://demo.playwright.dev/todomvc/ |
| Reqres | 練習用API（認証・CRUD対応） | https://reqres.in/ |

### 選定基準
- ログイン機能がある（認証テストが書ける）
- 複数のページがある（画面遷移テストが書ける）
- API が公開されている（API テストも書ける）

**おすすめ**: Sauce Demo + Reqres の組み合わせ。E2E（Sauce Demo）とAPI（Reqres）を両方カバーできる。

### 課題 9-1
Sauce Demo（https://www.saucedemo.com/）にアクセスし、手動で一通り触ってみる。「ログイン → 商品をカートに入れる → 購入手続き」の流れを体験し、テストすべきポイントを3つ以上メモする。

## レッスン 9-2: テスト計画書を作る

### このレッスンで学ぶこと
「何を・なぜ・どこまで自動化するか」を文書にまとめる。

### たとえ話
家を建てる前に設計図を書くのと同じ。いきなりテストを書き始めるのではなく、全体像を計画してから着手する。

### テスト計画書のテンプレート

```markdown
# テスト計画書: [アプリ名]

## 1. テスト対象
- アプリのURL
- 主要な機能の一覧

## 2. テスト範囲
- 自動化するテスト（理由とともに）
- 自動化しないテスト（理由とともに）

## 3. テスト種別
- E2Eテスト: 画面操作のテスト（○件）
- APIテスト: データ通信のテスト（○件）
- スモークテスト: 最低限の動作確認（○件）

## 4. テスト環境
- ブラウザ: Chromium
- ツール: Playwright
- CI/CD: GitHub Actions

## 5. テストケース一覧
| No | テスト名 | 種別 | 優先度 |
|----|---------|------|--------|
| 1 | ログインできる | E2E | 高 |
| 2 | ... | ... | ... |
```

### QA視点
テスト計画書はマニュアルQAでもおなじみのはず。自動化でも同じ思考プロセスが必要。「なぜこのテストを選んだか」を言語化できることが、エンジニアとしての信頼につながる。

### 課題 9-2
Sauce Demo に対するテスト計画書を上のテンプレートに沿って作成する。最低5つのテストケースを含める。

## レッスン 9-3: E2E + APIの統合テスト

### このレッスンで学ぶこと
E2Eテスト（画面操作）とAPIテスト（データ通信）を組み合わせた実践的なテストを書く。

### プロジェクト構成

```
tests/
├── e2e/
│   ├── login.spec.ts        — ログインテスト
│   ├── cart.spec.ts          — カート操作テスト
│   └── checkout.spec.ts      — 購入フローテスト
├── api/
│   ├── users.spec.ts         — ユーザーAPIテスト
│   └── posts.spec.ts         — 記事APIテスト
└── smoke/
    └── health-check.spec.ts  — 最低限の動作確認
pages/
├── login-page.ts
├── inventory-page.ts
└── cart-page.ts
```

### E2Eテストの例（Sauce Demo）

```typescript
import { test, expect } from '@playwright/test';
import { LoginPage } from '../../pages/login-page';

test('正しい情報でログインできる', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('standard_user', 'secret_sauce');
  await expect(page).toHaveURL(/inventory/);
});

test('間違ったパスワードでログインできない', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('standard_user', 'wrong_password');
  await expect(loginPage.errorMessage).toBeVisible();
});
```

### 課題 9-3
テスト計画書に書いたテストケースのうち、優先度「高」のものから順に実装する。最低3つのE2Eテストと2つのAPIテストを書く。

## レッスン 9-4: ポートフォリオの仕上げ

### このレッスンで学ぶこと
プロジェクト全体を「人に見せられる」状態に仕上げる。

### READMEに書くべき内容

```markdown
# テスト自動化ポートフォリオ

## プロジェクト概要
テスト自動化の学習と実践のためのプロジェクト

## 使用技術
- Playwright（E2Eテスト）
- Postman / Newman（APIテスト）
- GitHub Actions（CI/CD）
- Allure（レポート）

## テスト対象
- Sauce Demo（ECサイト風デモアプリ）
- JSONPlaceholder / Reqres（練習用API）

## 実行方法
npm install
npx playwright test

## テストレポート
GitHub Pagesで公開: [URL]
```

### GitHub上での見せ方
- READMEにバッジ（テスト結果のステータスアイコン）を追加する
- テスト計画書をリポジトリに含める
- learning-log で学習過程を見せる（成長ストーリーが伝わる）

### 課題 9-4
1. READMEを上のテンプレートに沿って充実させる
2. GitHub Actionsのバッジをmain READMEに追加する
3. テスト計画書をリポジトリの `docs/` フォルダに保存する

---

## よくあるつまずきと対処法

### テストケースが多すぎて何から書けばいいかわからない
**対処**: テスト計画書の「優先度: 高」から着手する。まず3つ書いて動かすことを目標にする。完璧を目指さない。

### Sauce Demoのログインユーザー名やパスワードがわからない
**対処**: ログインページに使用可能なユーザー名とパスワードが記載されている。`standard_user` / `secret_sauce` が基本。

### プロジェクト構成が複雑になってきて混乱する
**対処**: まず上のフォルダ構成を参考に空のファイルだけ作る。「設計図」を先に作ってから中身を埋めていく。
